Status: **implemented — canned semantics proven by tests; lnd adapter selected

## The honest sandbox limitation

The phase-4 drill (`scripts/lnd_regtest_drill.py`) reproduces reliably in
this sandbox:

- **Stage 1 PASS** — bitcoind 29.0 regtest up, 101 blocks mined.
- **Stage 2 PASS** — two lnd nodes initialized (GenSeed → InitWallet with
  captured seeds, TLS, macaroons, gRPC) and both wallets ACTIVE.
- **Stage 7 PASS** — SIGTERM → restart → unlock → wallet ACTIVE again.
- **Stages 3–6, 8 BLOCKED** — on `--bitcoind.rpcpolling` (zmq-free chain
  sync), the **btcwallet block-processor never credits on-chain outputs**,
  so channel funding cannot complete in-sandbox. This is the upstream
  btcwallet/chain-sync subsystem family (lnd #9108, #10389, #11004), NOT an
  lnd API defect — lnd 0.21.x CI pairs with bitcoind 29.x cleanly.
- The zmq loopback **currently probes OK** (`scripts/zmq_probe.py` returns a
  round-trip), yet the stall persists on both zmq (undeliverable through
  lnd's block subscription here) and rpcpolling paths — the stall is in the
  btcwallet block-processor, not the transport. Diagnosed across rpcpolling,
  neutrino, restarts, and forced `recovery_window` rescans.

Consequence: the live regtest payment drill (open → invoice → pay → settle)
is an **open item**, tracked below with the exact instrument to re-run it.
Everything else was built against the real contract and proven by the
offline suite (the API/ledger layer cannot tell which provider answered).

## Architecture

```
apps / Mini App ──► FastAPI /api/v1/lightning/* ──► lightning_service (payment_intents + XP ledger)
                                                      │
                                       make_lightning_provider(settings)
                              ┌─────────────────────┴─────────────────────┐
                              ▼                                           ▼
                 CannedLightningProvider (default)              LndLightningProvider (mode=lnd)
                 lnd-identical semantics in memory              gRPC → lnd v0.21.4-beta
                 (dev/test; disclosed as such)                  (pinned stubs, generated from the
                                                                 release's own .proto set)
```

- `lightning_adapter/state.py` — the canonical invoice/payment state
  machines; **both** providers obey them.
- `lightning_adapter/lnd_stubs/` — gRPC stubs generated by
  `scripts/gen_lnd_stubs.py` from lnd **v0.21.4-beta's own protos**
  (the same pinned-revision approach as the DSH manifest, D8).
  Version-specific API facts captured by the drill and encoded in the
  generator/provider: the state enum is `WalletState`
  (`RPC_ACTIVE`/`SERVER_ACTIVE` are the ready states), v0.21.4 removed
  `seed_entropy` from `InitWalletRequest`, the router stub class is
  `RouterStub`, and lnd authenticates with `macaroon` **metadata**
  (not bearer tokens).
- The node admin surface is never exposed to the agent runtime.

## State machines

Invoice (receive): `pending → settled | expired`
- lnd reports elapsed invoices as `CANCELED`; our API surfaces them as
  `expired`. Settlement of an expired invoice is refused (410).

Payment (send): `prepared → authorized → in_flight → succeeded | failed`
- `prepare` = fee preview + **authorization digest** binding
  `(payment_hash, amount, fee_limit)` — nothing moves;
- `authorize` = the digest the user saw must be presented back (mismatch → 409);
- `submit` = node submission with the fee-limit cap; outcome terminal,
  uncertain node outages map to **504** (never silently retried).

## Idempotent settlement (acceptance: duplicate callbacks)

`POST /lightning/invoices/{hash}/settle` applies a settlement through a
double gate:

1. provider verification — the preimage must hash to the payment_hash;
2. **CAS row transition** `pending → settled` (rowcount gate) — the race
   loser credits nothing;
3. XP ledger `credit_purchase` with idempotency key `purchase:{intent_id}` —
   a replayed entry can never double-apply.

Test: `test_duplicate_settlement_credits_exactly_once` posts the settlement
**six times** and asserts exactly one ledger entry, one balance increase,
and `credited=false` with an explicit replay note on every duplicate.

## Fee preview + authorization (acceptance: fee handling)

- published policy: `base_fee_msat` + `fee_ppm`, hard cap
  `lightning_max_fee_msat` (10 000 msat default);
- `prepare` returns the estimate (clamped + `fee_clamped` flag when the
  router estimate exceeded the cap) and the digest;
- `submit` enforces the cap at the node (`fee_limit_msat` on SendPaymentV2).

## Recovery and backups (acceptance: documented + tested)

lnd recovery model, documented and scripted:

1. **Static Channel Backups (SCB)** — `ExportChanBackup` →
   `channel.backup` bytes; restorable via `RestoreChanBackup` (drill stage 8)
   and round-tripped by the canned provider with a checksum
   (`test_scb_roundtrip_and_checksum`).
2. **Restart drill** (drill stage 7): SIGTERM → restart → unlock → wallet
   ACTIVE again (**PASS in-sandbox**).
3. **Data-loss drill** (drill stage 8): wipe node data → re-init wallet
   from the captured seed (`recovery_window=500`) → `RestoreChanBackup` →
   DLP force-closes the channels from the SCB and sweeps funds on-chain.
   BLOCKED in-sandbox by the stage-3 stall; the scripted instrument is the
   re-run path.

Runbook (production):
- nightly: `ExportChanBackup` → write SCB blob to durable storage next to
  the node seed backup (seed is required to restore);
- node lost: install lnd, re-init wallet from seed, restore SCB before
  first start, let DLP force-close and sweep — funds recoverable without
  channel.db;
- restart: lnd replays from its own channel.db; unlock via macaroon TTL.

## Node health & liquidity disclosure (acceptance: users informed)

- `GET /lightning/health` — mode, synced_to_chain/graph, pubkey, channels;
- `GET /lightning/channels` — per-channel capacity/local/remote +
  **user-facing disclosures** ("payments route over your channel
  liquidity; low capacity may cause failures until channels are opened or
  rebalanced") and an `inbound_constrained` flag under
  `lightning_min_inbound_msat`;
- `GET /lightning/capabilities` — mode ("canned semantics provider" is
  disclosed verbatim in dev/test), fee policy, sats→XP conversion
  (published + `can_change: true`), custody notes, mainnet gate.

| `PaymentRejected` (definite) | 422 |
| `NodeUnavailable` (outcome unknown) | 503 |
| `PaymentUncertain` (submitted, terminal unseen) | 504 |

## Open items (honest list)

1. **Live regtest payment drill**: re-run `make lightning-drill` on a host
   where the btcwallet block-processor credits outputs (or with lnd ≥ 0.22
   and the blockbeat fixes) to complete stages 3–6 and 8 (fund → channel →
   invoice → pay → settle → DLP). All API/ledger behavior is already
   contract-tested; stages 1, 2 and 7 pass in this sandbox.
2. **Real settlement webhook**: the settle endpoint currently accepts the
   preimage directly (dev seam, verified cryptographically). In production
   it must be called by the node's invoice-settled stream
   (`SubscribeInvoices`) with the node-supplied preimage — the service
   layer is already shaped for it.
3. **Channel management** (open/close/rebalance) is intentionally out of
   scope for phase 4's wallet surface; ops runs the node.
4. `EstimateRouteFee` fallback: when the router cannot estimate, the
   policy fee is used and the response is flagged — verify against mainnet
   routing economics during the security review gate.
5. Send-side reconciliation: a payment left `in_flight` by a 504 needs a
   periodic `payment_status` reconciliation pass to reach a terminal state;
   the provider method exists, the scheduler hookup is phase 5+.
